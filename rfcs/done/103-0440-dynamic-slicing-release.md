## 1. Summary

Bump the lock-step family `0.43.0` → `0.44.0` and prepare the release of RFC-102. Preparation only:
**no tag, no publish** — both remain separate owner authorizations.

## 2. Why now — the trigger is the owner, and this RFC says so plainly

RFC-094 gives three triggers for a minor. **Two of them have not fired:**

```text
two themes accumulated  -> NO. RFC-102 is one theme.
28 days since the last  -> NO. 0.43.0 shipped 2026-08-04; this is day 4.
the owner asks          -> YES. This is the whole basis for the release.
```

This is the **second** owner-directed release, after `0.42.0`. `0.43.0` fired on its own terms. The
record should not later read as though the cadence produced this one: it did not, and RFC-094
explicitly permits the owner to ask without justifying it. Recorded so the release table stays honest
about which releases the policy generated and which it merely allowed.

The owner asked, on the record, after a risk review that found no correctness issue and one
documented behavioural hazard (RFC-102 §8.1). Nothing here is a policy exception needing repair.

## 3. Release content — one theme, and it is a `Changed`

**RFC-102 — slicing on dynamic tensors.** `slice()` and `slice_str()` now accept dynamic tensors and
return a dynamic tensor sharing storage with its source.

This release is **`Changed`-only**. It adds no public item: `slice()` and `slice_str()` already
existed with identical signatures. What changed is that they stop returning
`MattenError::Unsupported`, which is observable to anyone matching on it.

```text
RFC-101 / 0.43.0 was Added-only and forbade an empty `Changed` heading.
RFC-103 / 0.44.0 is the inverse: Changed-only, and must NOT emit an empty `Added` heading.
```

### 5.0 How this measurement was taken, and two defects in my first attempt

Per rule 002 §6, the pattern's matches were proven, not assumed. My first pipeline was **wrong
twice**, and both errors under-counted:

```text
grep -v "Cargo.lock"  -> unanchored, so it dropped any LINE mentioning Cargo.lock,
                         not just the file. Lost 2 lines. Reported 57, not 59.
grep -c "<filename>"  -> matched that path CITED INSIDE another file, inflating one
                         file's count. Reported 9 for a file that has 11.
```

Corrected by enumerating `git ls-files`, excluding `Cargo.lock` by **exact path**, and counting per
file. Re-derive with that method; do not trust a tree-wide `grep -rn | wc -l`.

### 5.1 `introduction.md` — a content rewrite, not a number swap

Lines 19–25 currently read, in part:

> *"tracks the current 0.43 release family, an RFC-099 and RFC-100 release … **No existing behavior
> changed** — see the `[0.43.0]` CHANGELOG entry."*

**"No existing behavior changed" becomes false under this release.** A number-only bump would leave a
publishable falsehood on the documentation's front page. Rewrite the paragraph to describe RFC-102,
and state the behaviour change rather than eliding it.

### 5.2 `public-api-snapshot.md` — one sentence, and no new row

Its head paragraph says core's API *"most recently changed in RFC-099 … and RFC-100."* **That stays
true** — RFC-102 adds no public item and changes no signature.

Follow the **RFC-088 precedent already recorded on that page**: RFC-088 extended `slice_str`'s
grammar and got a sentence noting it *"changed no public item — a signature-level grammar extension
behind an existing method, not a new row here."* RFC-102 is the same shape. Add a comparable
sentence; **do not add a row, and do not move the "most recently changed" claim.**

## 6. CHANGELOG

A `[0.44.0]` entry with **`Changed` and `Version` only**. No `Added`, and no empty `Added` heading.

### 6.1 Claims that would be publishable falsehoods

```text
- "adds dynamic slicing" as an ADDITION. It removes an error from methods that
  already existed. Added is the wrong section and the wrong verb.
- silence about storage sharing. A slice retains its SOURCE'S ENTIRE allocation
  (RFC-102 §8.1). If the entry mentions sharing as a benefit it must mention the
  retention cost, exactly as compatibility.md and slicing.md now do.
- "no existing behavior changed" — the boilerplate from 0.43.0's entry. The
  opposite is true here.
- any claim about numeric slicing changing. It did not; 35 pre-existing tests
  pass unmodified.
```
